# 自动增量翻译

入口：平台 → 商家翻译 → 选择商家、语言 → 自动增量翻译。

默认关闭，需管理员为每家商户、每种语言单独开启。先发布初始语言包，再开启自动维护。开启时记录现有商品基线，不把历史缺译/失败内容当成新商品全部重跑。自动发布是独立开关；关闭时新译文保存在数据库和翻译记忆中，管理员手动发布后才更新前台。

## 处理规则

- 商品、SKU、分类、分类关联、公开报价数据的事务性触发器记录变更；数据库事务回滚时变更通知也回滚。
- 独立进程每 5 秒检查轻量变更计数；默认等 30 秒合并连续修改，持续修改最长合并 5 分钟。正在解析/导入文件时等待；每 10 分钟做一次指纹补偿检查。
- 指纹只包含可展示文本。价格、图片及纯版本号修改不请求 AI。实际内容变化才进入任务，SKU 文本、商品名、分类及规格选项统一去重翻译。
- 自动增量使用配置中心实时 AI 模型、超时、并发与重试。手动全量保持 Batch；断点继续保持原执行方式。API 与自动进程的实时请求共用 Redis 并发租约及 RPM 额度，Redis 不可用时不绕过限制。
- 自动/手动共用数据库语言级唯一任务约束；暂停任务不会被自动恢复，历史失败文本不会在每次扫描时无限重试。失败批次和错误沿用现有任务记录，可手动重试或微调。
- 写回前重新核对源文与人工微调；变更后的旧响应不覆盖新源文，人工译文优先。发布按完整商品组复用已保存文本，无额外模型调用；不完整商品组保留旧语言包内容。
- 后台自动状态每 5 秒轻量刷新，显示等待、排队、自动翻译、暂停、待复核、待发布。读取未完成或失败时不以 0 冒充实际进度，也不允许重复手动启动。

## 发布配置

本功能需要数据库迁移 `20260906_0134`，迁移后必须运行现有 `db-grants`，让导入 worker 也能写入事务性变更通知表。不能仅替换前端或跳过迁移。

迁移在启用触发器的同一事务中，将变更通知表所需的最小权限授予现有 `atc_app` / `atc_worker`（部署 Compose 固定的角色），避免旧服务在迁移与授权容器启动之间写入失败。完整运行时授权同样改为一次事务提交，失败则回滚，不暴露中间的撤权状态；不放宽租户 RLS。

两个生产 Compose 配置均新增 `translation-worker`，使用与 API 相同的镜像、数据库、Redis、翻译密钥和对象存储配置：

```sh
python -m app.workers.catalog_translation
```

标准发布脚本在网站 API/Web 恢复服务后再更换该 worker。它不作为 API 健康检查的依赖；翻译耗时、失败或暂停均不会使正常网站容器变为不健康。单独重启 API 不暂停自动任务。

独立 worker 通过 PostgreSQL advisory lock（本地 SQLite 为文件锁）选主；每个 PostgreSQL 任务另有持有期锁，避免新进程回收仍在旧进程执行的任务。重启后只恢复本进程拥有的自动任务，复用已成功保存的内容；进程被强杀时，尚未保存的在途实时请求可能需要重试。

本地调试应使用单独测试数据库和本地语言包目录，不要将测试进程指向共享开发库或生产 R2。`tests/test_translation_automation.py` 覆盖调度、隔离、暂停、去重、缓存发布、变更事务与并发限制；所有测试不调用付费翻译接口。

验证记录（2026-09-06）：功能、翻译、架构及部署配置相关测试 128 项通过，前端构建和 10 语言控件校验通过。SQLite 完整迁移及 PostgreSQL 迁移 SQL/RLS 结构已检查；未连接生产 PostgreSQL 执行迁移。扩展 API 回归另有 222 项通过后遇到报价草稿切回中文仍保留英文名称的已有失败，该断言在修改前 HEAD 的独立副本同样失败，未将此无关修复混入本功能。
