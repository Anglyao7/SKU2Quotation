# 客服 AI 运行契约 v2.1

> 状态：Accepted for implementation  
> 版本：2.1
> 生效日期：2026-08-11
> 适用范围：商家前台文字客服、后台客服辅助与其共享的知识和证据基础设施  
> 关联设计：[智能客服开发设计](./CUSTOMER_SUPPORT_AI_DEVELOPMENT.md)

## 1. 目的

本契约定义客服 AI 在生产环境中可以读取什么、可以回答什么、必须引用什么、
何时允许调用业务工具、何时必须停止并转人工，以及每次回答必须留下哪些审计证据。

本契约不是 Prompt，也不能依赖模型“自觉遵守”。所有关键边界必须由数据库约束、
查询过滤、字段白名单、工具权限和服务端验证共同执行。

本文使用以下规范词：

- **MUST（必须）**：违反即视为安全或正确性缺陷，不得上线。
- **MUST NOT（不得）**：任何环境都不能依赖模型绕过。
- **SHOULD（应该）**：默认实现，只有记录明确理由后才能偏离。
- **MAY（可以）**：按产品阶段选择实现。

## 2. 范围与非目标

### 2.1 本契约覆盖

- SKU 与商品公开知识的投影、检索和回答。
- 企业上传文件的扫描、解析、版本化、检索和引用。
- 客服对话中的上下文、语言、证据、回答验证和人工接管。
- 价格、库存、订单等实时数据的只读工具调用。
- AI Run、证据、模型、Prompt、工具和结果的可追溯记录。
- 上线前评估、灰度发布、线上监控和回归要求。

### 2.2 v1 不覆盖

- AI 自主退款、取消订单、修改报价、写入客户资料或其他不可逆操作。
- 让模型直接执行 SQL、访问任意 URL、读取对象存储任意对象或选择租户。
- 用企业资料训练基础模型。
- 自动把客服历史、客户上传内容或人工回复加入企业知识库。
- 在证据不足时使用模型自身知识补全企业事实。

上述能力若以后需要开放，必须通过新契约版本增加独立的权限、确认、幂等、审计和
回滚规则，不能仅增加一个 Tool 或修改 Prompt。

“不得补全企业事实”不等于“无检索结果时不得回答”。模型可以提供明确标注为通用建议的
分析、帮助客户缩小需求或提出一个聚焦的追问，但不得借此声称某个店铺商品、价格、库存、
政策或承诺真实存在。

## 3. 核心不变量

以下不变量优先于回答率、速度和自动化率：

1. **租户隔离**：每次知识检索、工具调用、证据读取和会话写入都必须绑定服务端解析的
   `tenant_id`；模型和客户端不得提供或覆盖该值。
2. **默认拒绝**：未进入字段白名单、未分类、未审核或没有显式授权给客服 AI 的内容，
   默认不可被投影、检索或发送给模型。
3. **来源优先**：企业事实只能来自本次 Run 的有效知识证据、受控工具结果，或管理员批准
   且随 Run 留存哈希的企业对客资料；不得用模型预训练知识替代企业事实。
4. **企业事实有据**：店铺、商品、价格、库存、订单、政策和企业承诺等企业事实必须关联
   至少一条有效证据。未引用证据的回复只能是通用建议、澄清问题或明确的无匹配说明，
   不得暗示店铺具有某项商品或能力。纯寒暄只能引用企业对客资料中的店铺名称、公开简介
   和服务范围，不得借寒暄补充其他企业事实。
5. **动态数据实时查询**：价格、库存、订单状态等快速变化的数据不得以历史向量作为
   当前事实回答。
6. **最小权限**：客服 AI 只能看到完成任务所需的字段，只能调用当前阶段允许的工具。
7. **证据不可变**：历史回答必须绑定当时使用的来源版本和证据快照；来源更新不能改写
   历史记录。
8. **安全降级**：任何模型、检索、验证或工具故障都不得变成无依据的企业事实；系统应
   优先继续由 AI 给出安全说明或追问，只有满足第 12 节授权原因时才转人工。纯寒暄生成
   失败时使用本地安全文案并保持 AI 接待，不得无故转人工。
9. **人工优先**：客户明确要求人工后，AI 必须停止自动处理；人工客服回复后，AI 不得
   自动重新接管，除非客服或工作流明确恢复。
10. **全程可审计**：任何已经发送的 AI 消息必须能定位到唯一 AI Run、模型版本、策略
    版本、证据和工具调用。
11. **店铺归属**：`tenant_id` 对应一个店铺。启停、文件知识、SKU 投影、企业提示词、检索
    阈值、置信度阈值、模型绑定和运行记录都以店铺为边界；`organization_id` 只表达客户
    企业归属，不能让同企业店铺自动共享知识。
12. **平台管理边界**：API、知识库、店铺启停、Prompt、阈值、试跑和内部 Run 审计只对
    平台管理员开放。店铺成员只在客服工作台查看和处理本店会话，不获得 AI 管理接口。
13. **检索与决策解耦**：向量或关键词检索只负责提供证据，不拥有人工接管决策权。
    `0` 条证据、低检索分数或 Embedding 降级本身都不是 `HANDOFF` 原因。

## 4. 数据边界

### 4.1 数据处理类别

| 类别 | 示例 | 处理方式 |
|---|---|---|
| 稳定且允许面向客户的知识 | 商品名称、公开描述、规格、用途、品牌介绍、公开 MOQ | 版本化后进入 RAG |
| 动态业务事实 | 当前价格、库存、上下架状态、订单、报价、实时交期 | 通过只读工具实时查询 |
| 内部经营信息 | 成本、利润、采购价、供应商、内部评分、内部备注 | 不进入客户 AI 上下文 |
| 机密或受限信息 | 密钥、Token、密码、未授权个人信息、法律保留资料 | 不进入模型或向量库 |

向量是派生索引，不是事实源。原始规范化文本、来源版本、审核状态和定位信息必须保留，
且删除或撤销来源时必须能使其向量失效。

### 4.2 知识分类

每个知识来源必须有且只有一个 `classification`：

| 分类 | 含义 | 客户 AI 是否可用 | 客户能否打开完整来源 |
|---|---|---:|---:|
| `PUBLIC` | 内容和来源都可公开 | 是 | 是 |
| `CUSTOMER_APPROVED` | 内容允许用于客户回答，但原文件不公开 | 是 | 否，只能展示安全标题或摘录 |
| `INTERNAL` | 仅供企业成员使用 | 否 | 否 |
| `CONFIDENTIAL` | 仅限特定内部角色 | 否 | 否 |
| `RESTRICTED` | 不允许进入任何模型上下文 | 否 | 否 |

`classification`、可用受众和引用展示方式是三个独立概念，不得用“文件存在于私有 R2”
推断内容一定不可用于客服，也不得用“AI 可以使用”推断客户可以下载原文件。

### 4.3 来源可用性

每个来源还必须包含：

- `customer_agent_enabled`：是否允许客户 AI 检索。
- `staff_copilot_enabled`：是否允许后台客服辅助检索。
- `approval_status`：`DRAFT`、`APPROVED`、`REVOKED`。
- `citation_mode`：`LINK`、`EXCERPT`、`LABEL`、`NONE`。
- `customer_citation_title`：经过审核的客户可见标题。
- `locale`：来源主要语言。
- `effective_from`、`effective_until`：可选的生效时间。

客户 AI 只能检索同时满足以下条件的来源：

```text
tenant_id = 当前会话商家
customer_agent_enabled = true
classification IN (PUBLIC, CUSTOMER_APPROVED)
approval_status = APPROVED
status = ACTIVE
当前时间处于有效期内
citation_mode != NONE
```

这些条件必须在数据库查询或检索服务中强制追加，不能由模型生成过滤条件。

## 5. SKU 客服字段策略

### 5.1 默认允许进入客服知识投影

以下字段只有在所属商品/SKU 已发布且内容经过确认后才可进入：

- 公开商品编码、商品名称、公开描述、分类和默认单位。
- 公开 SKU 编码、名称、选项和标签。
- 明确标记为客户可见的条码。
- 已确认且允许客户查看的规格、材质、用途、认证和市场属性。
- 商品或 SKU 的公开 MOQ 与单位。
- 经过审核的包装、使用、保养和兼容性说明。

### 5.2 永远不得进入商品知识投影或 Embedding

- 供应商 ID、名称、代码和其他可识别供应商身份的信息。
- 供应商 SKU。
- 供应商评分、质量评分、履约评分和评分方法。
- 采购价、供应商报价、成本、利润、毛利率和内部定价规则。
- 采购备注、内部备注、审核记录和员工评论。
- `AI_SUGGESTED`、待审核、被拒绝或未发布的属性。
- 密钥、对象存储私有地址、内部文件路径和访问凭证。

该禁止规则同时适用于 canonical payload、chunk 文本、chunk metadata、Embedding 输入和
检索响应，不得只在最终回答阶段删除。

### 5.3 MOQ 与交期规则

- MOQ 可以进入客服知识，但必须去除供应商关联，只表达经过批准的产品/SKU 起订规则。
- 存在多个供应商 MOQ 时，投影器必须使用明确的客户侧聚合规则或保留为不带供应商身份的
  可解释选项；不得让模型自行猜测默认 MOQ。
- 商品知识的 `OVERVIEW` 必须包含公开 MOQ；SKU 级 MOQ 同时保留 SKU 对应关系。客户未指明
  SKU 且存在多个值时，客服只能列出可用选项或追问，不得擅自选择一个值。
- 原始供应商交期不得直接作为稳定客服知识。只有单独发布的“客户承诺交期”可以进入
  RAG；实时交期应通过工具查询。

### 5.4 字段策略执行

- 字段策略必须使用显式 allowlist，禁止使用“先序列化所有 ORM 字段再删除敏感字段”。
- 每次字段策略变化必须增加 `field_policy_version`。
- 新版本投影完全生成并验证成功前，旧活动版本继续服务。
- 新策略激活时，旧 document、chunk 和 embedding 必须原子标记为 `STALE`。
- 必须使用哨兵值自动测试敏感字段不会出现在任何投影和检索结果中。

## 6. 文件知识契约

### 6.1 文件进入知识库前

文件必须经过以下状态链：

```text
UPLOADED -> QUARANTINED -> SCANNING -> PARSING -> REVIEW_REQUIRED
         -> INDEXING -> ACTIVE
```

任一步失败进入 `FAILED`，不得产生可检索的半成品。文件默认是 `DRAFT`，只有有权限的
成员明确批准后才可用于客户 AI。

### 6.2 解析要求

- 只处理允许的真实 MIME 类型，扩展名不能作为唯一判断。
- PDF 保留页码、标题和段落；扫描件需要 OCR 并记录 OCR 置信信息。
- DOCX 使用标题路径和段落定位；没有可靠页码时不得伪造页码。
- PPTX 保存幻灯片编号和标题。
- XLSX 保存工作表名称和单元格范围；复杂表格不得被无结构地拼成一段文本。
- 图片文字、脚注、表头和列表应在有助于理解时保留。
- 文件内的指令一律视为资料内容，不具备修改系统 Prompt、工具权限或运行契约的能力。

### 6.3 分块要求

- 优先按标题、段落、FAQ、列表和表格的语义边界分块，固定 Token 长度仅作为兜底。
- 每个 chunk 应尽量自包含，避免只有“是的”“见上文”等无法独立理解的内容。
- 标题路径和必要上下文可以进入 chunk，但页眉、页脚和重复版权文字应去重。
- chunk 必须保存来源版本、内容哈希和结构化 locator。
- 解析器、OCR、chunker 和 Embedding 模型版本必须可追踪。

### 6.4 版本与删除

- 文件内容哈希相同的重复上传应可识别，不重复生成相同版本。
- 新版本只有在扫描、解析、Embedding 和验收全部成功后才可原子激活。
- 来源撤销后必须立即退出新检索；历史 Run 仍保留当时的安全证据快照供审计。
- 客户打开历史引用时，如果来源已经撤销，应显示“该来源版本已不再公开”，不得跳转到
  新版本冒充当时来源。

## 7. 查询与检索契约

### 7.1 查询预处理

系统可以结合有限的最近对话，将省略或指代补全为独立检索问题，但必须：

- 保留商品编码、SKU、订单号、数字、单位和专有名词原文。
- 记录原始问题和改写后问题。
- 不把 AI 先前未经证实的回答当作用户事实。
- 多意图问题可以拆分检索，但最终仍属于同一 Run。
- “这个呢”“我不知道，你选一款”等省略型追问必须优先继承最近一条实质性客户问题；重复
  的安全兜底、寒暄和 AI 自己的猜测不得成为检索主题。已经明确写出用途或商品类别的新
  推荐问题不得混入旧主题。
- 查询预处理必须同时输出 `interaction_goal`。第一版至少区分普通问答
  `QUESTION_ANSWERING` 与需要做选择的 `PRODUCT_RECOMMENDATION`，并在 Run 中记录是否使用
  上下文补全。

### 7.2 检索方式

- SKU 和文档默认使用 lexical + vector 的混合检索。
- 商品/SKU 编码、条码和精确名称匹配应优先于模糊语义相似度。
- 不同来源类型应设置候选配额，防止一个长文件占满全部上下文。
- 候选结果应统一重排，并记录 lexical、semantic、rerank 和最终分数。
- 检索分数只能用于排序和支持度判断，不能作为模型“自信度”。

### 7.3 权威性与冲突

默认权威顺序为：

```text
成功的实时只读工具结果
  > 当前活动且客户已批准的结构化 SKU 数据
  > 当前活动且客户已批准的企业文件
  > 不回答企业事实；可以提供通用建议或追问
```

来源发生实质冲突时不得静默拼接。系统应优先选择更高权威和更新版本；无法确定时必须
说明存在冲突并转人工或请求澄清。

### 7.4 无答案规则

出现以下任一情况时，不得生成确定性事实回答：

- 没有满足边界条件的证据。
- 证据与问题只存在弱相关关系。
- 关键数字、型号、时间或适用条件在来源中缺失。
- 来源互相冲突且无法按权威规则解决。
- 回答需要未授权工具或客户身份尚未验证。

允许的回答动作是：

- `ANSWER`：证据充分时回答企业事实；没有证据时只能回答明确标注的通用建议。
- `CLARIFY`：提出一个有助于继续检索或判断需求的聚焦问题。
- `NO_MATCH`：明确说明当前未找到店铺内的匹配项，并给出下一步筛选方向。
- `HANDOFF`：仅限第 12 节定义的授权原因。

回答动作必须与 `grounding_mode` 分开记录：`EVIDENCE` 表示企业事实有据，
`GENERAL_GUIDANCE` 表示没有把模型常识当作企业事实。没有证据时必须使用
`GENERAL_GUIDANCE`，不得仅因无证据进入 `HANDOFF`。

### 7.5 商品推荐决策

推荐不是检索结果展示。`PRODUCT_RECOMMENDATION` 在存在当前公开商品证据时必须：

- 先明确给出一个主推荐，再说明当前假设和有证据支持的理由；不能把多个候选平铺后让客户
  自己重新做选择。
- 最多补充一个确有不同取舍的备选，回答中最多使用两个商品引用；不得把向量分数当成推荐
  理由展示给客户。
- 结构化输出写入 `recommended_citation`，该编号必须指向本 Run 的 SKU 商品证据并在正文
  中实际引用。服务端校验失败时不得发送原草稿。
- 客户说“不知道”或“你来选”时，允许基于已知信息做明确标注为初步选择的推荐；可以在
  推荐之后只问一个高信息量问题，不能先发通用问卷阻断回答。
- 没有商品证据时不得编造店铺商品；模型仍应使用 `GENERAL_GUIDANCE` 给出选择思路或一个
  聚焦追问，并保持 AI 接待。
- 如果首轮模型已经给出有效主推荐且所有事实安全校验通过，但因引用商品过多而不符合展示
  契约，编排器可以执行一次受限重写：保留模型选出的主商品，只向模型提供该商品和一个
  备选的公开证据。重写仍未通过时才进入 `RETRIEVAL_FALLBACK`，不得发送原始商品列表。

## 8. 证据与引用契约

### 8.1 Evidence 是一等数据

每条进入回答上下文的证据必须有服务端生成的不可猜测 ID，并至少记录：

- `evidence_id`、`run_id`、`tenant_id`。
- 来源类型、来源 ID、不可变来源版本 ID、document ID、chunk ID。
- 原始 locator 和客户安全 locator 快照。
- 本次使用的安全摘录、摘录哈希和来源内容哈希。
- 检索查询、候选排名、各阶段分数和是否最终选用。
- 是否被引用、引用序号和支持的 claim。
- 来源分类、引用模式、客户可见标题和来源版本时间。

### 8.2 Locator 规范

| 来源 | 必须保存的定位信息 |
|---|---|
| Product/SKU | `product_id`、可选 `sku_id`、字段或 section path、记录版本 |
| PDF | 文件版本、页码、标题路径、段落或块编号 |
| DOCX | 文件版本、标题路径、段落编号 |
| PPTX | 文件版本、幻灯片编号、标题 |
| XLSX | 文件版本、工作表、单元格范围或表格名称 |
| Tool | 工具调用 ID、工具版本、查询时间、记录版本和安全结果哈希 |

### 8.3 客户引用模式

- `LINK`：显示客户可见标题、版本/更新时间，并链接到安全公开页面。
- `EXCERPT`：显示客户可见标题和经过策略过滤的相关摘录，不开放原文件。
- `LABEL`：只显示客户可见标题、资料类型和版本时间。
- `NONE`：不得用于客户 AI 的事实回答。

客户界面永远不得展示 R2 对象键、签名 URL、内部文件名、内部 ID、检索分数或
`INTERNAL/CONFIDENTIAL/RESTRICTED` 内容。

### 8.4 引用生成与校验

- 模型只能引用本次 Run 提供的 `evidence_id`，不得生成 URL、页码或来源标题。
- 客户可见编号、标题、链接和定位文字由服务端根据证据渲染。
- 每个企业事实 claim 必须映射至少一个 evidence；多个证据可以共同支持一个 claim。
- 服务端必须拒绝不存在、跨租户、未选中、已撤销或客户不可引用的 evidence ID。
- Grounding 校验必须比较回答 claim 与证据内容；仅验证 ID 存在不等于事实受支持。
- 寒暄、致谢、追问和转人工说明不要求引用。

### 8.5 安全社交回复

- 仅短且纯粹的问候、致谢和告别可以进入 `GREETING`、`THANKS`、`FAREWELL` 分支；包含
  商品、MOQ、交期、公司事实或其他问题的混合消息必须进入正常 RAG/工具流程。
- 规则只负责高精度分流，正常回复必须调用当前店铺绑定的生成模型，不能把固定文案作为
  主路径。
- 模型上下文只能包含店铺名称、管理员批准的企业对客简介、对客服务范围、客户语言和
  受限会话历史；内部智能体说明和系统提示词不是企业事实来源。
- 社交回复不展示引用，但 Run 必须保存 `intent`、`grounding_mode`、模型/Prompt 版本、
  企业对客资料字段清单及内容哈希，并把 `retrieval_count` 记为 0。
- 模型输出仍需通过语言、长度、数字、链接、敏感信息和接管意图校验。失败、模型不可用或
  达到自动回复日限额时使用对应语言的安全兜底，保持 `AI_ACTIVE`，不得切换人工接管。

## 9. 回答生成与验证契约

### 9.1 结构化结果

模型必须返回符合固定 schema 的结果，例如：

```json
{
  "detected_language": "zh-CN",
  "response_action": "ANSWER",
  "grounding_mode": "EVIDENCE",
  "answer": "这款产品的公开起订量为 100 件。[1]",
  "confidence": 0.86,
  "citations": [1],
  "recommended_citation": null,
  "handoff_reason": null
}
```

`response_action` 只能是：

- `ANSWER`：证据充分，可以发送答案。
- `CLARIFY`：缺少必要信息，只发送一个清晰追问。
- `NO_MATCH`：说明没有找到店铺匹配项，但继续提供安全的筛选建议。
- `HANDOFF`：命中第 12 节授权原因，需要人工处理。

`grounding_mode` 只能是 `EVIDENCE` 或 `GENERAL_GUIDANCE`。`ANSWER + EVIDENCE`
必须带有效引用；`CLARIFY`、`NO_MATCH` 和 `GENERAL_GUIDANCE` 不强制引用，但仍需通过语言、
数字、链接和敏感信息校验。

`recommended_citation` 仅在 `PRODUCT_RECOMMENDATION + EVIDENCE` 时必须为有效 SKU 商品引用；
普通问答和无商品证据的通用建议必须为 `null` 或省略。推荐契约校验与事实引用校验都通过
后才可发送。

### 9.2 发送前验证

发送客户前必须依次通过：

1. JSON/schema 和最大长度校验。
2. tenant、会话状态和 AI 是否仍有接管权校验。
3. 引用 ID、来源状态、引用模式和 claim 映射校验。
4. Grounding、矛盾、数字和单位一致性校验。
5. 敏感字段、PII、密钥、内部链接和越权内容校验。
6. 输出语言、品牌语气和允许链接校验。
7. 重复回复、循环和最大回合数校验。

任何强制校验失败均不得发送原草稿。系统可以在受限次数内重新生成；仍失败时发送对应
语言的安全追问或暂时无法确认说明，并保持 AI 接待。只有模型或确定性策略输出第 12 节
授权原因时才允许人工接管；纯社交回复按 8.5 节降级。

## 10. 工具契约

### 10.1 v1 允许的工具

第一阶段只允许无副作用的只读工具，例如：

- 查询当前公开价格。
- 查询当前可售和库存状态。
- 查询当前客户承诺交期。
- 在完成客户身份校验后查询其订单或报价状态。

### 10.2 强制边界

- 工具必须由服务端注册表提供，模型不能构造任意函数、SQL、URL 或请求头。
- `tenant_id`、当前用户身份和权限由服务端注入，不暴露为模型可填写参数。
- 工具参数使用严格 schema，标识符必须再次核对租户归属。
- 工具只返回回答所需的安全字段，不得把完整 ORM/第三方响应交给模型。
- 工具输出视为不可信数据，必须校验并记录安全快照。
- 每个调用都有超时、有限重试、熔断和安全错误码。
- 工具失败不得回退到旧向量或让模型猜测实时数据。

### 10.3 未来写操作

任何写操作至少需要：

- 独立的权限和允许场景。
- 明确的用户确认和确认内容快照。
- 幂等键、前置状态检查和操作限额。
- 可审计的前后状态和可行时的补偿/回滚路径。
- 高风险阈值与人工审批。

在这些规则进入新契约版本前，客服 AI MUST NOT 执行写操作。

## 11. 对话、记忆与多语言

- 使用有限的最近消息和受控会话摘要作为上下文，不无限发送完整历史。
- 摘要必须标记“用户事实”“工具事实”“AI 未证实陈述”，不得混为一体。
- 客户消息和人工回复不得自动成为企业知识；只有经过审核发布的内容可进入知识库。
- 回答默认使用访客当前语言；商品代码、SKU、数字和单位保持原意。
- 跨语言检索可以使用多语言 Embedding 或翻译后的检索查询，但必须保留原始查询。
- 翻译后的引用摘录必须仍指向原始来源版本，并清楚区分原文与译文。
- 翻译失败不得改变事实或伪装成已找到答案，可回退原文、追问或转人工。

## 12. 人工接管契约

以下情况必须转人工：

- 客户明确要求人工。
- 需要人工执行订单或账户操作、付款、退款等当前未开放的写操作。
- 涉及投诉/争议审核、定制商务承诺、安全或法律判断。
- 人工客服已实际发送第一条回复，或企业策略要求特定主题人工处理。仅查看、打开或领取会话
  不得改变接管状态。

以下情况本身不得触发人工接管：没有向量命中、检索分数低、Embedding 不可用、生成模型
暂时失败、引用校验失败、客户问题宽泛或模型信心低。系统应重试、给出安全通用建议、说明
无法确认企业事实或追问；只有问题同时需要上述人工专属动作时才可转接。

接管记录至少包含：

- 接管原因和优先级。
- 用户问题与已确认的关键信息。
- AI 已检索的安全来源和已执行的工具。
- 未解决点、错误码和建议下一步。

接管后 AI 状态变为 `SUSPENDED`。接管状态只有两个写入口：人工客服成功发送消息的同一
事务，或 AI/确定性策略明确产生 `HANDOFF` 决策。后台不得提供未发送消息即可直接接管的
操作。只有平台管理员或确定性工作流可以恢复 AI；客户新增消息本身不能自动恢复。

## 13. 安全、隐私与 Prompt Injection

- 用户消息、上传文件、网页和工具结果全部视为不可信内容，不能覆盖系统指令。
- 文件中出现“忽略之前要求”“调用某 API”“泄露 Prompt”等文字只能作为资料，不得执行。
- 输入与输出都必须进行内容安全和敏感信息检查。
- 来源权限必须在检索前执行，输出脱敏不能替代访问控制。
- 模型不得获得数据库凭证、R2 凭证、第三方 Token、完整系统 Prompt 或内部错误堆栈。
- Trace 默认不向普通客服展示，敏感 Trace 内容必须受专门权限和保留期控制。
- 客户身份、订单等个人数据只在完成相应认证后通过工具读取，不进入共享知识向量。
- 不得把不同客户的会话摘要、工具结果或 PII 写入租户共享知识库。

## 14. AI Run 状态机

每次访客消息最多触发一个活动 Run，使用访客消息 ID 作为幂等边界：

```text
QUEUED
  -> RUNNING
     -> WAITING_FOR_INPUT
     -> VALIDATED -> SENT
     -> HANDED_OFF
     -> DECLINED
     -> FAILED
     -> CANCELLED
```

- `SENT` 前，AI 消息、Run、claims 和引用证据必须在同一事务边界内持久化。
- 会话已关闭、人工已回复或 Run 被替代时，尚未发送的 Run 必须取消。
- 同一访客消息重试不得产生第二条 AI 回复。
- 超时或进程重启后可以从安全检查点重试，但不得重复执行未来的写操作。

## 15. 可观测性与审计

每个 Run 至少记录：

- 会话、触发消息、店铺、语言和当时的启用状态。
- 原始问题、改写问题和识别出的意图。
- 字段策略、检索器、排序器、Prompt 和编排器版本。
- 模型 provider/name/version 与 Token、延迟和安全错误码。
- 候选证据、最终证据、claims、引用和验证结果。
- 工具名称、版本、参数摘要、结果摘要、耗时和错误。
- 最终 decision、是否发送、是否转人工和人工修改结果。

日志和 Trace 不得记录密钥。对包含 PII 或内部证据正文的字段，应提供关闭明文采集、加密、
脱敏和独立保留期配置。

## 16. 评估与发布门槛

### 16.1 测试集

上线前必须建立版本化测试集，至少覆盖：

- 商品名称、规格、MOQ、用途和对比问题。
- 企业品牌、政策、文件页码和跨文件问题。
- 无答案、模糊问题、错误型号和冲突来源。
- 多语言、错别字、连续追问和多意图。
- 供应商、成本、内部备注和跨租户窃取尝试。
- Prompt injection、伪造引用、越权工具和要求人工。
- 模型/Embedding/字段策略/Prompt 变更后的回归。

### 16.2 核心指标

- Retrieval Recall@K 和精确标识符召回率。
- Answer correctness、claim groundedness 和 citation precision。
- 无答案识别率与应转人工场景召回率。
- 非法引用率、跨租户泄漏率和敏感字段泄漏率。
- 工具选择正确率、参数正确率和失败降级正确率。
- p50/p95 延迟、Token、单次成本和人工修改率。
- AI involvement、AI resolution、handoff、repeat contact 和客户评分。

### 16.3 硬性上线门槛

- 跨租户、敏感字段、伪造引用和未授权工具的阻断测试必须 100% 通过。
- 任何客户可见 AI 消息必须具有完整 Run；事实性回答必须具有有效 evidence。
- 相同测试集相对已批准基线不得出现未解释的质量回退。
- 新模型、Prompt、检索权重、字段策略和 parser 版本必须先通过离线回归与不对客户发送的
  平台验证流量。

自动化率不能作为单独上线依据。错误地自动解决比正确转人工更严重。

## 17. 店铺状态、模型绑定与灰度

面向店铺的智能客服状态必须只有两种：

| 状态 | 行为 |
|---|---|
| `关闭` | 不为新的客户消息创建 AI 回答；人工客服保持可用 |
| `启用` | 在本契约的证据、阈值、引用、限额和转人工约束内自动回答 |

草稿评估、离线回放和不发送流量属于平台发布流程，不得暴露成第三种店铺运行状态。只有
平台管理员可以切换店铺启停；操作必须写审计日志，并能立即停止新 Run。商家客服发送
第一条回复时自动接管单会话，但不能仅靠查看、领取或点击状态按钮接管，也不能恢复 AI
接待。

平台维护可复用的模型 API 配置档案。每个店铺绑定一个档案，也可使用平台默认档案；同一
档案可以批量绑定到多个店铺，不同客户或店铺可以绑定不同档案。复制店铺配置时可以选择
复制模型绑定、提示词和阈值，默认不复制启用状态；文件知识和 SKU 数据永远不复制。

## 18. 故障与降级

- Embedding/检索故障：降级到安全的关键词检索；仍无证据时不回答企业事实，由 AI 追问或
  给出通用建议并记录降级原因。
- 生成模型故障：不发送半成品；普通问答使用对应语言的安全追问并保持 AI 接待。商品推荐
  已检索到公开 SKU 证据时，允许服务端按检索顺序生成带真实引用的“主推荐 + 最多一个备选”
  初步选择，并把 `generation_mode` 记录为 `RETRIEVAL_FALLBACK`；不得把它伪装成模型推理。
- 引用或 Grounding 验证失败：不得删除引用后发送，必须重试或改为不包含企业事实的安全
  追问，不得因为验证失败自动转人工。
- 工具超时：说明暂时无法确认实时信息并继续收集必要信息；只有确需人工执行的事务才转接，
  不使用旧值冒充当前值。
- 新知识版本构建失败：继续使用旧活动版本，并在后台显示失败状态。
- 翻译失败：保留原消息和来源，不改变事实；按语言策略降级。
- 整体 AI 服务停用：现有人工客服会话仍可正常收发消息。

## 19. 变更管理

以下变化必须增加对应版本并触发评估：

- 字段允许/禁止规则：`field_policy_version`。
- canonical payload 或 chunk 结构：`schema_version`/`chunker_version`。
- Embedding 模型：provider/name/model_version/dimensions。
- 检索、重排和阈值：`retrieval_policy_version`。
- Prompt、工具集合和编排逻辑：`prompt_version`/`orchestrator_version`。
- 回答 schema 或引用规则：本运行契约版本。

契约升级必须附带数据迁移、索引重建、回滚方式和回归结果。历史 Run 始终记录运行当时的
版本，不随当前配置变化。

v2.1 变更不修改知识 chunk 或 Embedding，因此不需要数据迁移和索引重建；运行时记录
`orchestrator_version=3`、`base_prompt_version=2`、`recommendation_policy_version=1` 与
客服商品重投影 `field_policy_version=2`。该字段策略只允许客户安全的标量规格选项进入
Evidence，剔除内部元数据、供应商、采购/成本、内部备注、评分和联系方式字段。
回滚时恢复 v2 编排器与 Prompt 即可，既有 Run 的版本和证据快照保持不变。上线前必须通过
推荐意图、上下文继承、推荐引用契约、模型超时检索兜底及既有数字/敏感字段回归用例。

## 20. v1 验收清单

1. 客户 AI 无法检索其他租户、未批准、过期或已撤销来源。
2. 供应商名称/编码/SKU/评分、采购成本和内部备注不会进入投影、Embedding 或回答。
3. MOQ 可以从批准的商品/SKU 证据中回答并正确引用。
4. 文件回答能定位到真实来源版本及页码、标题、段落、幻灯片或单元格范围。
5. 模型伪造 evidence ID、URL 或页码时，服务端拒绝发送。
6. 来源更新后新回答使用新版本，历史回答仍能审计旧版本。
7. 价格、库存和订单状态只来自受控工具，并带查询时间证据。
8. 客户明确要求人工或命中人工专属事务时能正确接管；证据不足、来源冲突、Embedding/工具
   故障只阻止企业事实断言，不会自动接管。
9. 人工接管后 AI 不会自行恢复或重复回复。
10. 每条已发送 AI 消息都有完整 Run、版本和验证结果；事实性回答具有 claims/evidence，
    纯社交回复具有 intent、企业对客资料哈希和生成/兜底方式。
11. `hi`、`你好` 等纯寒暄调用店铺模型并保持 AI 接待；`Hi，MOQ 是多少？` 不得绕过 RAG。
12. 每个店铺只能在启用/关闭之间切换；启停、提示词、阈值、文件知识和 SKU 检索严格按
    店铺生效。
13. 平台可以批量绑定或复制 API/策略配置，但不能借此复制文件知识、SKU 或历史会话。
14. 商家成员只能访问本店客服会话；知识库、启停、Prompt、阈值、模型/API、试跑和内部
    Run 审计接口均返回平台管理员权限错误。
15. 历史租户角色中的 AI 管理授权不会绕过平台管理员身份校验。
16. 商品推荐问题会复用现有商品混合检索成果，省略型追问能继承最近客户主题；有商品证据
    时必须给出一个带引用的主推荐而不是结果列表，生成模型故障时仍返回可审计的检索兜底
    推荐；没有商品证据时生成通用建议或聚焦追问，且不会伪造店铺商品事实。
17. 关键安全测试、离线测试集和平台验证流量达到第 16 节门槛。
